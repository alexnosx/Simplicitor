## Remaining and new findings

### R2-01: P1, qualification enumerates the wrong installation context

B4, plan lines 1024-1027: `ProductsEx('', '', 1)` enumerates USERMANAGED. A normal per-user MSI belongs to USERUNMANAGED, which is 2. The fresh-profile check can pass with zero products, but Assert-Installed then finds no newly installed Simplicitor product and fails. Use a named constant with value 2 and verify the returned current-user context. Keep ProductCode-based identity.

Evidence: [Microsoft SDK Msi.h](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/Msi.h) defines USERMANAGED=1, USERUNMANAGED=2, MACHINE=4; [MsiEnumProductsEx](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msienumproductsexw) describes the contexts.

### R2-02: P1, source changes still bypass busy protection and omit a type notification

C2.4, lines 1855-1863: set_paths mutates the roster and emits inspection even when busy. Disabling page widgets does not protect this public method or a screen-level drop handler. MainWindow currently ignores a new operation while one is running, so a changed roster can receive the old inspection result. Retain the existing set_paths busy guard and guard drop/remove/browse routes.

At lines 1911-1914, forcing Excel blocks the combo's signals and never emits file_type_changed afterward. MainWindow will not clear a loaded PowerPoint template, and the type-dependent placeholder/template presentation can remain stale. Update the type once, notify the controller once, and invalidate setup once, before the new inspection snapshot is emitted. Add a PowerPoint-template-to-source-route regression check.

### R2-03: P1, inspection terminal states and Cancel need explicit handling

Only show_inspection clears `_inspecting`. A failed or cancelled inspection reaches show_failure/show_status and then set_busy(False) through today's MainWindow callbacks; none of those instructions resets the reading flag. Next can remain disabled after the worker is gone. Define an inspection-finished path for success, failure and cancellation, with a visible recovery action and preserved setup.

The set_busy example (lines 1889-1893) disables the entire pages stack, ignores `saving`, and does not update Cancel. A Cancel button inside those pages cannot remain usable. Keep Cancel outside the frozen setup or disable editable controls individually. Enable it only for cancellable extraction work, disable it during Save As, and test cancellation through the MainWindow/worker path. Preserve saved-candidate acknowledgement and stale-result rules.

### R2-04: P1, finish MainWindow integration rather than replacing references mechanically

C2.6's replacement for lines 101-112 omits the creation, disabling and hiding of `_edit_panel`, while the prose says to keep its handlers. Current `_connect_signals` and `_start_ollama_worker` still reference that object. Explicitly retain its construction before signal setup, or remove its unused connections coherently while retaining the legacy modules required by templates. Copying the replacement block literally without that initialization breaks window construction.

Current `_start_extraction` calls panel.set_busy(True, saving=...) and then workspace.set_busy(True). Replacing both with CreateScreen calls repeats busy_changed and can override the Save As setting with the default saving=False. Remove the former workspace call from extraction start/finish; retain one busy update for generation and templates. Collapse duplicate connectivity updates too.

Preserve the existing worker-to-GUI slot declaration for show_status (or route progress through a GUI-thread Slot). The new method lacks the decorators used by ExtractionPanel even though worker.progress still connects directly to it. Check thread affinity with a controlled worker; this review did not execute a cross-thread experiment. [PySide signal/slot guidance](https://doc.qt.io/qtforpython-6/tutorials/basictutorial/signals_and_slots.html#thread-affinity).

### R2-05: P2, the confirmation test and pending-confirmation sequence disagree

C2.5's test (lines 1962-1968) uses show_inspection(()) and then expects Extract to emit. Today's retained confirmation behavior treats empty documents as not inspected, requests inspection again, and sets `_pending_confirm`. The C2.4 show_inspection example also does not resume pending confirmation. Use a real synthetic SourceDocument in this test and specify how pending confirmation resumes.

When resuming a pending Extract operation, dispatch it after the inspection worker's finished handler has cleared `_extraction_thread`; emitting it during inspection_ready can hit MainWindow's busy guard and silently drop it. Cover this lifecycle with a controlled worker, not only a patched `_start_extraction` that never sets busy state.

### R2-06: P2, screenshots still start real backends and can close with live threads

C2.7 constructs real MainWindow, then set_paths emits a real inspection request. The script manually calls show_inspection(()) and set_columns while that worker can still be running. This can produce disabled controls, overwrite staged state, or leave Edit disabled at the final click. MainWindow also starts Ollama discovery. `window.close()` can defer closing while workers stop, but the script returns without draining that shutdown.

Use inert discovery/inspection behavior for the capture tool and wait for all window-owned threads to finish on close, following the existing pytest teardown pattern. Keep the live extraction walkthrough separate. Profile isolation is already correct; the remaining issue is deterministic state and lifetime.

### R2-07: P2, qualification should observe executable version and prove repair

B4 reports executable_version as `"$version.0"` without reading the installed executable's VersionInfo. Assert and record the observed ProductVersion. During the probe, the MSI version changes to 2.1.99 but the unchanged executable must still report 2.1.0.0.

The repair check operates on an intact installation. On the hosted runner only, remove one known packaged file, repair, and verify its restored hash. Keep removal constrained to the verified test installation. This does not authorize any local installer/repair/removal operation.

### R2-08: P2, build tests write the new fragment to a production workspace path

B3 adds FRAGMENT=ROOT/.nuitka/msi/payload.wxs, but today's payload fixture patches only DIST_DIR, ICON and NUITKA_CACHE_DIR. The mocked build therefore writes the fragment outside its tmp_path. Patch FRAGMENT to a path under tmp_path and redirect other build intermediates that tests write. The policy's claim that every test-created file lives only in `.venv/test-home` or `.venv/pytest-tmp` is stronger than the current suite guarantees; do not equate temporary-file cleanup with removing installed software.

### R2-09: P2, the PowerShell parse-check command expands $null in the caller

B4 line 1170 uses an outer double-quoted -Command string. When run from PowerShell, the calling shell expands `$null` before starting the child shell, leaving an invalid assignment. Use a single-quoted command argument or call Parser.ParseFile directly. Parsing must not invoke the qualification script or msiexec. No parser or qualification command was executed during this review.

### R2-10: P2, the PDF privacy test covers only PdfGenerator

The new generator's failure log is sanitized. Its production route still uses FileGenerator, GenerateWorker and MainWindow, which currently log output paths or errors containing those paths. MainWindow derives filenames from the prompt, so those logs can contain confidential words. Extend the synthetic privacy check to the PDF route and sanitize inherited path logging while keeping useful paths in the UI. The direct PdfGenerator test alone does not establish pipeline log privacy.

### R2-11: P2, persist the updated testing rule in repository policy

AGENTS.md still prohibits install/uninstall/delete tests as one blanket category. That contradicts Alex's new permission for the local suite and temporary-file operations. Task 0 should update the testing rule in AGENTS.md and the packaging procedure alongside the CI split, preserving historical test records. Your current explicit instruction takes precedence; future workers should not need missing chat history to resolve this conflict.

## Generated MSI components: checked boundary

The fragment handles XML attribute escaping, stable identifiers, explicit HKCU key paths, every payload file, and removal rows for nested directories. Pinned WiX 5.0.2's [FinalizeComponentGuids](https://github.com/wixtoolset/wix/blob/v5.0.2/src/wix/WixToolset.Core.WindowsInstaller/Bind/FinalizeComponentGuids.cs) generates registry-keyed GUIDs without applying the file-keypath branch's file-count restrictions. Current general schema wording is more restrictive; it is not evidence that this pinned generator cannot compile.

Per-folder grouping means a component's resources can change when the payload changes, while its registry-derived GUID remains stable. The chosen early major-upgrade removal reduces that overlap risk. Record that support is for this private payload and major-upgrade route; do not infer minor-update/patch compatibility from the same-payload probe. If adding that support later, reassess component granularity against [Microsoft component-code rules](https://learn.microsoft.com/en-us/windows/win32/msi/changing-the-component-code). No compiled MSI or ICE validation result was produced during review.

## Testing-policy assessment

The policy matches Alex's rule in intent and workflow triggers:

- Local source tests are allowed, including creation/removal of synthetic temporary files. Their build subprocesses must remain mocked; a test must not start Nuitka, dotnet tool restore, msiexec, or qualification on this PC.
- Installers, uninstallers, msiexec, Windows Sandbox and the qualification script are prohibited locally. Dependency/tool installation is not implicitly authorized by permission to run tests.
- Pushes and pull requests run the tests job. The build job requires workflow_dispatch or a version tag and depends on tests. Ordinary feature pushes no longer run the full build.
- The listed manual full runs are milestone runs: Task 0 baseline, B5, C2.7 and D1. A release tag is another milestone and still requires an explicit go. Check the dispatched run's exact head SHA, not simply the newest run on main.
- Fix R2-08's temporary-path claim and R2-11's stale repository instruction. Those are policy/documentation consistency issues; the updated rule does not prohibit ordinary file-deletion tests.

The review file and generated map are the only intended changes in this review commit. The plan, application, workflow, build and qualification code remain unchanged. No merge, implementation, tag, release or publication is authorized by this document.
