## Findings

### F1 (P1): the model gate passes replies that discard the requested paragraph

**Evidence:** A8 `check` (lines 2952-2965) checks substrings, word count and paragraph count. Most tasks have no check for the wording that their instruction requires preserving. The approved design requires mechanical checks of paragraphs outside the instruction's target, not just bytes outside the selection.

I ran the real evaluator offline with the same lossy fake-answer construction used by `test_evaluate_counts_passes_and_gate`: concatenate each task's `required` strings, duplicate that text to reach the count, then append its `keep` paragraphs. The production validation and candidate builder accept it, and the evaluator reports **12/12, zero verification failures, pass**. Examples:

- Replace the payment period: the whole paragraph becomes just `45 days`.
- Replace only `short`: the whole paragraph becomes just `brief findings report`.
- Rename two headings: both become `Introduction Details`.
- End two paragraphs with exclamation marks: both become `new page! final report!`.
- Polite requests: the checks do not require each paragraph to start with `Please`.

The successful fake-client test therefore demonstrates false acceptance. The six structural checks cannot compensate: these are structurally valid, lossy edits inside the selection.

**Correction:** Give the existing twelve tasks checks specific to their instructions. Exact replacements, exact heading renames and punctuation-only edits should compare the complete expected paragraphs. Adding a sentence must preserve the original wording; adding a list item must preserve the existing items and their order. Check the first word of each polite-request paragraph. Keep flexible checks for genuine rewrites, with the facts they must retain. Replace the lossy passing fake answers with valid answers and add negative tests using these lossy replies. Recompute the reported scores after these corrections when Alex authorizes the model run. Do not use the current scores to settle D4.

### F2 (P2): amendment A1 can move a bookmark's meaning while every check passes

**Evidence:** A5 `align` (lines 2165-2190) maximizes similarity subject only to nondecreasing assigned indices; equal counts skip similarity altogether. Validation checks that every marked source has some output, not that the paragraph associated with its bookmark was retained in the right place. A3's marker checks preserve the raw stream but cannot detect a bookmark now attached to different text. This contradicts the plan's Review Focus 2 claim that moving a bookmarked paragraph is rejected.

Synthetic input: a bookmarked Heading 1 `Alpha heading`, followed by `Body one` and `Body two`. Reply: `Body one`, `Alpha heading`, `Body two`, `Added`. Alignment returns `[0, 0, 2, 2]`; validation and all six verification checks pass. The saved first paragraph is `Body one`, with Heading 1 formatting and the `Alpha` bookmark. The unchanged `Alpha heading` has moved to the second paragraph and has no bookmark. A monotonic sequence of assigned numbers did not establish monotonic paragraph identity.

**Correction:** Add an alignment guard for recognizable unchanged paragraphs: exact matches must retain their source identity and order, and an exact bookmarked paragraph found later must not have its marker assigned to unrelated text. Reject contradictory/ambiguous assignments instead of silently choosing a formatting source. Add reordered bookmarked-heading tests for both equal and unequal counts, plus the intended split, merge and inserted-list cases. State the limits of heuristic formatting assignment in the amendment; do not describe its bookmark behavior as unchanged until those cases pass. This requests no semantic verifier for arbitrary prose.

### F3 (P2): amendment A4 removes original tabs and line breaks from copied paragraphs

**Evidence:** A5 line 2203 calls unrestricted `rstrip()` on every output string. Input paragraphs `Name\t` and `Pay in 30 days.`, with a reply that copies the first exactly and changes only the payment period, produce saved paragraphs `Name` and `Pay in 45 days.`. The original tab is deleted by code, even though the model preserved it. The same applies to an original trailing line break or spaces. Deleted characters get no green added/replaced-character highlight.

**Correction:** Narrow the amendment to unwanted whitespace introduced by the model. Preserve an original trailing whitespace suffix on an unchanged/copied paragraph, and define how trimming relates to the aligned source before applying it. If that distinction cannot be made safely, retain line-ending normalization only. Add tests that an untouched paragraph retains its original trailing tab, line break and spaces while another selected paragraph changes; retain a separate test for genuinely added stray whitespace. The measurement about appended list whitespace does not justify removing existing document content.

### F4 (P2): the page limit does not use the extraction reader's calculation

**Evidence:** A2 `_page_cost` (lines 1164-1172) visits regular headers/footers only, omits their table cells, and counts body tables through `row.cells`, which repeats horizontally merged cells. Current `source_readers._read_docx` visits regular, first-page and even-page header/footer parts once and counts physical table cells through `row._tr.tc_lst`.

Two synthetic probes:

- Body text 899,500 characters plus a first-page header of 1,000 characters: extraction cost **301**, editor cost **300**, and `open_document` accepts it.
- One horizontally merged cell containing 451,000 characters: extraction cost **151**, editor cost **301**, so the editor would refuse a permitted file.

**Correction:** Use the existing reader's character-accounting rules for the editing limit, including distinct header/footer variants and physical cells. Share or copy the small deterministic counting logic without changing extraction behavior. Add exactly-at-limit and just-over-limit tests involving header variants and merged cells, not only long body paragraphs.

### F5 (P2): the reading view silently omits supported read-only table content

**Evidence:** A4 `build` (lines 1860-1890) reads body table cells using `c.text` and header/footer parts using only `part.paragraphs`. A synthetic document with `Outer` in a body cell, a nested table containing `Nested visible text`, and a header table containing `Header table text` produces only the body paragraph and a cell containing `Outer\n`. Neither table's omitted text is shown, and the header has no display block. The approved design explicitly says nested tables show as text and headers/footers are shown read-only.

**Correction:** Flatten nested-table text for display and include table text in distinct header/footer parts, keeping all of it read-only. Add reading-view tests for these constructs and for first/even-page variants. This is display coverage, not permission to edit tables or a new layout renderer.

### F6 (P2): verification rescans the assembly buffer rather than the saved candidate's main part

**Evidence:** A3 `_verify` (lines 1565-1610) reads other parts and paragraph count from `new_data`, but performs the outside-byte, XML, text and bookmark checks on the separate `new_xml` argument. Those checks need to cover the actual candidate bytes.

I replaced `patch.rebuild` with a test wrapper that changes `Pay in 45 days.` to `Tampered words.` in the ZIP's main part while leaving its paragraph count unchanged. `build_candidate` returns a verified candidate whose saved text is `Tampered words.`; the text check passed against the untampered assembly buffer. This is a fault-injection probe of the promised verification boundary, not evidence that the current normal rebuild corrupts files.

**Correction:** Read the main part from `new_zip` and require it to equal the assembled `new_xml`, then perform checks 2, 3, 5 and 6 on that actual part. Add a corruption test targeting the packaged main part, alongside the existing other-part and splice-buffer corruption tests.

### F7 (P2): invalid XML Unicode reaches patching instead of proposal rejection

**Evidence:** A5 `_XML_INVALID` excludes control characters and U+FFFE/U+FFFF but not U+D800-U+DFFF. `validate` accepts a JSON string containing an escaped lone surrogate (`"bad\ud800"`); `build_candidate` then raises `UnicodeEncodeError`. The worker sanitizes that into a generic failure, but A8 catches only `EditError`, so such a response aborts the evaluation without its per-task report. The design requires invalid XML characters to be rejected as an unusable proposal.

The parser also accepts an unexpected top-level property despite the schema's `additionalProperties: false`; Ollama's output constraint does not replace validation of returned data.

**Correction:** Validate the complete XML 1.0 character ranges, including rejection of lone surrogates, before encoding or patching. Validate the required object shape and reject extra properties. Add escaped-surrogate and additional-property tests; an invalid model reply must give the normal unusable-proposal result in both the worker and evaluator.

### F8 (P2): Part B hashes an arbitrary existing destination on the GUI thread

**Evidence:** B1 rule 8 (line 3153) tells MainWindow to call `save.destination_state` before starting the save worker. That function calls `destination.read_bytes()` and SHA-256 over the whole existing file. The destination has no size limit and may be on a slow drive. This makes Save As acceptance a blocking GUI operation, contrary to the approved design's worker-owned save checks. It can also raise `EditError` before any worker exists; B1 specifies outcomes from the worker but no handler for this earlier failure.

**Correction:** Start the accepted-save worker immediately with the candidate and destination, capture the destination state as its first save operation, and retain that same state for the commit-point recheck. Adjust A7's setup/save path and B1's handoff explicitly so Part B does not have to invent that interface. Keep accepted-save cancellation/close behavior unchanged. Add a test that fingerprint failure reaches the Save-step outcome with the candidate retained, and that GUI handling itself performs no destination read. Preserve the deliberate optimistic race limitation in the design.

### F9 (P2): the gate record cannot identify or qualify the tested model build

**Evidence:** A8 `evaluate` (lines 2987-3008) stores the model name and only `get_model_info(...)["details"]`, dropping any other metadata. It records no model digest, although the approved design requires one. It silently accepts missing metadata and never checks the reported Q4_K_M quantization. The C1 command uses generic tags while the following text says to substitute installed quantized tags. Therefore a passing JSON record is not sufficient to establish which candidate build was qualified.

**Correction:** Record the resolved installed tag, digest, quantization and actual request settings through the existing client or a narrow metadata addition. Fail qualification clearly when the selected candidate identity/quantization cannot be established or differs from the planned candidates. Use the resolved tags in C1's command. Add fake-metadata tests for identity retention and wrong/missing quantization. This is evaluation provenance, not a product model/hardware eligibility check.

### F10 (P2): the Word-check commands can inspect stale samples and return success on failures

**Evidence:** C2 uses a fixed output directory and runs the builder and Word checker as consecutive commands without checking the builder's exit code. The builder returns 2 when the directory is nonempty; a later Word check could still open six files from an earlier run. The checker (lines 3093-3103) catches each open failure, prints `FAILED`, and completes normally; it also succeeds with no matching files. Its PowerShell syntax parses with zero errors, but its process result is not a qualification result. The plan's manual requirement to read all six output lines helps, but does not establish that they came from the current build.

**Correction:** Stop immediately on a nonzero builder exit code. Require the exact six expected sample names before starting Word. Make the checker return nonzero if any file fails or the expected set is incomplete. Record the source commit and sample hashes with the Word version and per-file results, so the one-off evidence refers to freshly generated samples. Keep the read-only, repair-off behavior and no-installer boundary.

### F11 (P3): release-note claims exceed the specified display and Save behavior

**Evidence:** D1's draft notes (lines 3229-3230) say the new file is saved next to the original, rather than there by default, and that comments and tracked changes are shown. Native Save As permits a different folder. The approved design says comment bodies are not shown, and A4's `iter_inner_content` omits text wrapped in tracked insertions/deletions: the paragraph's read-only reason is shown, not a revision display.

**Correction:** Say the original folder is the default and the user chooses where to save. Describe these paragraphs as read-only with a reason; do not promise comment bodies or tracked revision text are displayed. No new comment/revision renderer is requested. The preservation and privacy sentences can remain.
