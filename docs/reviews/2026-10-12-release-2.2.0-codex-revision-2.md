## Remaining corrections

### F1. [P1] Resolve default and parent-placeholder text properties before deciding to discard layouts

**Plan locations:** B1 lines 1439-1489 (`_level`, `_inherited_styles`, `_runs`); lines 1668-1685 (`_mostly_on_slide`, `look_is_on_slides`). Affects R2 and R4.

`_level()` reads only `a:lvlNpPr/a:defRPr`. It ignores `a:defPPr/a:defRPr`, including the default paragraph properties in a shape's list style, layout/master list style and presentation/master text defaults. `_inherited_styles()` also gathers only the parent placeholders' list styles, not their paragraph defaults.

**Reproduced with default list styling:** a synthetic layout defines Georgia 36 pt navy titles and Verdana 18 pt body text in `a:lstStyle/a:defPPr/a:defRPr`, with no level-specific override. Capture reports Calibri for both, 44 pt black titles. When the slides explicitly repeat the same Georgia/Verdana fonts their layout already supplies, `look_is_on_slides` changes from false to true. That is a false override under the plan's rule and needlessly replaces the deck's original layouts with the generic template.

The separate layout paragraph-default probe has the same missing-style result. The current master-branded test modifies `p:txStyles/p:titleStyle/a:lvl1pPr`, which is the supported path; it does not cover these omissions. The original slide-level paragraph case is fixed and should stay.

Default paragraph styles are normal DrawingML, with level/run properties taking precedence when present. [Microsoft's DefaultParagraphProperties documentation](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.defaultparagraphproperties?view=openxml-3.0.1) defines `a:defPPr` and its `a:defRPr` child. Placeholder formatting inherits through layout/master parents. [python-pptx placeholder documentation](https://python-pptx.readthedocs.io/en/latest/user/placeholders-understanding.html).

**Correction:** merge level-specific properties with their default paragraph properties at each style source, then fall through to the next source property by property. Include the relevant layout/master placeholder text defaults in the inherited comparison. Capture and routing must use the same effective resolver. Use each slide's actual layout/master/theme context rather than always the presentation's first master. Add fixtures proving the captured font/size/color and the retained original-layout route when explicit slide formatting matches those inherited values; also prove that a real differing font/color still selects capture. Keep the agreed thresholds and font/color-only comparison unchanged.

### F2. [P1] Capture the effective background on the newly selected route

**Plan locations:** B1 lines 1588-1617 and 1648-1698 (`_own_fill`, `_read_deck`, `capture_style`); B3 lines 2371-2383 (`prepare_template`). New gap exposed by the R2 routing correction.

The reader collects each slide's own background and the first master's background, but never the slide layout's background. That is enough to determine whether a slide has its own background, but not enough to capture the background a user sees. After revision 2, fonts or logos can select capture even when the background is inherited from a layout.

**Reproduced:** three slides use a layout with a dark-green `0B3D2E` background and slide-local Georgia/Verdana white text. The new selector correctly chooses capture. Both captured backgrounds are None, the result reports only colors/fonts, and the generated base template retains its white background. The actual dark background has been lost. No PowerPoint rendering was needed to establish which background XML was retained.

**Correction:** keep two distinct facts: whether a slide owns a background for the routing threshold, and its effective background for capture. Resolve the latter from slide, layout and that layout's master, including the supported picture/solid fill paths. Do not count an inherited background as slide-local. Use effective backgrounds for cover/common-background selection and text readability. Add an end-to-end preparation/import test with a layout-only background plus local font styling, and a route test proving that background inheritance alone preserves the original layouts. The test should inspect the resulting background and contrast color as well as the summary.

This is an inheritance correction inside the existing capture scope, not a request to copy slide compositions or add another rendering engine.

### F3. [P2] Decode image data before accepting and reporting it as captured

**Plan locations:** B1 lines 1539-1577 (`_readable`, `_picture`, `_fill`); B2 lines 1938-1950 and 2054-2092 (`_average`, picture application). R3 remains partly resolved.

`_readable()` calls Image.open and reads image.size. Those read the header, not the pixel stream. `_set_background`/`_add_logo` can also accept the bytes through python-pptx's metadata path. `_average` catches a later decode failure and returns white, so it can conceal the problem while the invalid image is still embedded.

**Reproduced:** a synthetic PNG retains its recognizable 16x16 header and valid chunk CRCs, but has an invalid compressed pixel stream. Image.open succeeds; Image.load raises OSError. A readable deck containing that image imports with status ok, retains it as background and logo, and reports "Taken from your deck: colors, fonts, background, logo." The output contains the corrupt data. PowerPoint's handling was not tested; neither a repair dialog nor a crash is claimed.

**Correction:** force pixel decoding inside the existing guarded readability check before either capture path accepts the bytes. Retain the existing unsupported-format and oversized-image handling; do not enable truncated-image acceptance globally. A decode failure should omit that image and its summary component while retaining valid text/colors. Add a valid-header/corrupt-payload test through capture, shared preparation and import, and assert the bad blob is absent from the saved package. Leave genuine disk-write failures outside the image-degradation guard.

This follows Pillow's documented lazy-loading behavior: identification alone does not read the image data. [Pillow Image.open and load](https://pillow.readthedocs.io/en/stable/reference/Image.html).
