### Does the edge test reject the released border at 1.25?

Yes. With the old style-sheet border, the plan's image-render test at 1.25 measured top **0.2663**, bottom **0.3999**, left **0.2609**, right **0.5217**. It fails the required minimum of 1.0. All three planned image ratios failed before and passed after.

I also ran separate offscreen Qt test processes with `QT_SCALE_FACTOR=1.25` and `1.5`, using the application's Segoe UI/11-point font and input styles, and grabbed the actual widget image. The painted border passed at both scales and both requested window sizes, 1280x800 and 1024x640. At 1.25, its edge weights were approximately **1.68 to 1.76**; at 1.5, **2.51 to 2.57**. Restoring the baseline Edit widget in the scratch copy made both 1.25 cases fail again; the 1280x800 top weight was **0.2661**. The scratch fix was restored afterward.

This is a useful contrast/thickness regression test: the old border cannot pass it at 1.25. It does not establish that only 125% caused the installed symptom, since the old outline also fails at 100% and 150%. Offscreen rendering, including an actual Qt device-pixel ratio, is not a native installed-Windows visual acceptance check. Preserve that distinction when reporting the fix.

## Full-suite verification limitation

The intended plan contributes five tests to the 1,290-test baseline. I did not obtain a complete passing full-suite result:

1. The first isolated scratch run hit `PermissionError [WinError 5]` in the unchanged hard-link test `tests/extraction/test_jobs.py::test_save_as_refuses_existing_source_alias`. An isolated rerun reproduced the sandbox denial of `os.link`. Later the full run hung in `tests/test_main_window_extraction.py::test_complete_column_review_extract_save_and_confirmed_overwrite`; the 60-second dump reached `_on_candidate_ready` and `CreateScreen.show_candidate`. I stopped that owned test process.
2. After identifying the filesystem restriction, I ran the unchanged suite outside that sandbox with a 240-second process limit. It progressed without the hard-link failure, then hung in `tests/test_main_window_edit.py::test_late_result_after_opening_another_document_is_ignored`; the dump reached `_on_edit_opened`, `EditScreen.show_opened` and `_show`. The owned test process was stopped at the time limit. This run also collected two temporary reviewer scaling probes, so it was not a clean 1,295-case measurement.

These stacks do not establish a cause or attribute the hangs to the two proposed widget changes. The relevant methods are outside those changes. No application/test fix or reduced acceptance bar was introduced. Claude's claimed 1,295 pass remains unconfirmed by this review; obtain a clean complete run before treating the implementation as verified.

Retain the callback locations and say that the frozen methods lie outside the proposed edited blocks, but attribution to the new fixes or the earlier hosted issue remains unestablished. Say that hangs were observed with the collection mitigation present, without declaring the same cause persists.
